# Amazonize Rakuten

楽天市場をAmazon風のシンプルなUIにするChrome拡張（Manifest V3）。
「シンプル楽天」にインスパイアされたプロジェクトです。

## 機能

| 機能 | 対象ページ | 既定 |
|---|---|---|
| 商品ページをAmazon風の3カラムに再構成 | `item.rakuten.co.jp` | ON |
| 商品画像の拡大表示（←→キーで画像送り） | `item.rakuten.co.jp` | ON |
| 商品説明の画像を左のギャラリーへ集め、同じ画像を1枚にまとめる | `item.rakuten.co.jp` | ON |
| 商品動画をギャラリーに並べる（勝手に再生させない。再生ボタンを押したときだけ再生） | `item.rakuten.co.jp` | ON |
| 検索結果の広告枠を目立たなくする | `search.rakuten.co.jp` | ON |
| かごの合計金額パネル（ポイント差引後の実質価格つき） | `cart.step.rakuten.co.jp/cart` | ON |
| 商品ページのクーポンをその場で獲得 | `item.rakuten.co.jp` | ON |
| 商品ページを開いた時点でクーポンを自動獲得 | `item.rakuten.co.jp` | ON（ポップアップの「開いたときに自動で獲得する」で切れる） |
| 獲得したクーポンの一覧（自動・手動とも。新たに獲得できたものだけ、新しい順に100件） | ポップアップ | ON |
| 注文確認画面で最良クーポンに自動で切り替え | `cart.step.rakuten.co.jp/order-confirmation` | ON（確認なし。ポップアップで「適用前に確認する」にもできる） |
| キャンペーンをトップページから探して一括エントリー | `www.rakuten.co.jp` → `event.rakuten.co.jp` | ポップアップから手動実行 |
| エントリー済みキャンペーンの一覧 | ポップアップ | ON |

自動で「注文を確定」する操作は一切行いません。クーポンは、注文確認画面で使えるもののうち割引額がいちばん大きいものに自動で切り替えます（注文の確定は本人が押す）。

## インストール（Brave / Chrome）

1. `brave://extensions`（Chromeは `chrome://extensions`）を開く
2. 右上の「デベロッパーモード」をON
3. 「パッケージ化されていない拡張機能を読み込む」→ このリポジトリのルートを選択
4. コードを変更したら、拡張機能カードの再読み込みボタンを押してからページを再読み込み

> **パスに日本語が入っていると読み込みに失敗する。** Chromium系は `--load-extension` や「パッケージ化されていない拡張機能を読み込む」で非ASCIIのパスを渡すと「拡張機能を読み込めませんでした」で弾かれることがある。その場合は `C:srcamazonize_rakuten` のようなASCIIのみのパスに置く（またはコピーする）。

## 設定

ツールバーのアイコンからポップアップを開いて各機能をON/OFFできます。設定は `chrome.storage.sync` に保存され、ページ再読み込みで反映されます。

キャンペーンは、ポップアップの「トップから探してエントリー」を押すと、楽天トップページを裏で開いて `event.rakuten.co.jp` へのリンクを集め、1ページずつ裏タブで開いて「エントリーボタンがあるか／もう済んでいるか／そもそも特集ページか」を判定します。「見つけたらエントリーまでする」がONなら、未エントリーのものだけ押します。結果は保存され、ポップアップの「エントリー済み一覧」に出ます。

URLを自分で指定して実行したい場合は、同じ欄の「URLを指定して実行」から（`event.rakuten.co.jp` のURLだけ）。こちらもスキャンと同じく、そのURLのために開いた裏タブだけでエントリーし、結果を一覧に記録する。

どちらも実行中はアイコンのバッジに残りの件数が出る。ポップアップを閉じても実行は続き、開き直すと進み具合か前回の結果が出る。

### テスト

```
node --test
```

注文確認の自動切り替えは既定でON・確認なしで、本人の注文に直接効く。画面の操作はログインが要るので自動では回せないが、「どのクーポンに切り替えるか」は状態（`state-bridge.js` の `slim()` を通した形）だけで決まる。その判断（`coupon-model.js` の `collect` / `chooseSwitch`）と文言の解析を、下の「実機での検証状況」で実際に出たクーポンを実物の項目名で書いたデータで確かめている。`tests/load.mjs` が content script を Node の `vm` で読み込む（依存パッケージは無い）。

配布用のzipには `tests/` を入れない（`manifest.json` / `src/` / `icons/` だけでよい）。

### 保存したページで試す

楽天のページを毎回取りに行くと遅く、中身も日々変わる。`tools/harness.mjs` は実ページを通信ごとHARに保存し、以後はそれを再生して拡張を当てる（ページ側のReactも保存したJSがそのまま動く）。1ページ数秒で回る。

```
node tools/harness.mjs record https://item.rakuten.co.jp/<店>/<商品>/   # fixtures/ に保存
node tools/harness.mjs run                                            # 全部に拡張を当てる
```

`tools/out/` にスクリーンショットと結果のJSONが出る。商品ページでは「ギャラリーへ移した / 重複で消した / 説明に残した（理由つき）」画像が一覧で出る。

- playwright はリポジトリに入れていない。`PLAYWRIGHT_DIR`（既定は `~/.claude/tools/browser`）から読む。
- `fixtures/` と `tools/out/` は `.gitignore` 済み。画像込みで1ページ30〜45MBある。
- **ログインした状態では record しない。** HARにはクッキーやページの中身がそのまま入る。かご・注文確認は対象外。
- Playwright のHARはそのままでは再生できなかったので、保存時に2点直している。途中で打ち切られた通信（status -1）は再生すると応答が来ないまま止まり、DOMContentLoaded に届かない。本文は文字列で保存されて UTF-8 で送り返されるので、EUC-JP のままの charset では全体が文字化けする。
- 保存に無い通信（拡張が足した画像の縮小版など）は本物へ取りに行く。完全なオフラインではない。

### 設計方針

- **商品データは `#item-page-app-data` から読む。** 楽天の商品ページは商品名・価格・画像・説明・バリエーションを一括りにしたJSON（80KB前後）をHTMLに埋め込んでいる。DOMを漁るより桁違いに安定するので、ここを第一の情報源とし、欠けた項目だけDOM/metaから補う。
- **購入エリアは複製せず移設する。** `#rakutenLimitedId_aroundCart` をそのまま新レイアウトへ `appendChild` する。Reactが描画した要素だが、移設してもクリックハンドラが生きたままであることを実機で確認済み（移設後にボタンを押して、バリデーションが同じように発火することを確認）。
- **商品ページは DOMContentLoaded を待たずに組み立てる。** 商品データのJSON（`#item-page-app-data`）は body の末尾近くにあり、その直後に楽天のReactのバンドルが3本、同期スクリプトとして続く。DOMContentLoaded はこれらの取得と実行が終わるまで来ないので、以前はその間ページが真っ白だった。JSONの直後に節点が来た（= パーサーが読み終えた）時点で組み立てを始める。購入エリアの枠（`#rakutenLimitedId_aroundCart`）はHTMLに入っていて、中の `irc="Quantity"` などにバンドルが後から描き込むので、枠を先に移設しておけばボタンはその場で描かれる（移設後も選択・価格の切り替え・バリデーションが元のページと同じに動くことを確認）。保存した4ページで、表示までが 0.59〜1.14秒 → 0.27〜0.78秒になった。説明の画像の選り分けは、バンドルの取得と帯域を取り合わないよう DOMContentLoaded の後に回す。Reactが描くクーポン（トピックス欄）も、その後に拾い直す。
- **レビューの星と点数もJSONから読む。** `itemInfoSku.itemReviewInfo.summary` に `itemReviewCount` と `itemReviewRating` が入っている。評価はfloat32で埋め込まれるため `4.699999809265137` のような値で来るので、小数2桁に丸めて使う。星は「灰色の★5つ」に「橙の★5つ」を `width: (点数/5)*100%` で重ねて描くので、半端な点数も見た目に出る。
- **商品説明はDOMではなくJSONの文字列から組み立てる。** `pcFields.productDescription`（商品説明文）と `salesDescription`（販売説明文）。店舗のHTMLには楽天のテンプレートの `span`/`td` を先に閉じる「閉じタグ」が入っていることがあり、DOMの `.sale_desc` には `<style>` しか残らず、LPの画像17枚は隣の `div` にこぼれていた（以前は説明の大半を取りこぼしていた）。`DOMParser` で組み、`script` は除く。
- **説明の画像は左のギャラリーへ移す。** 同じ画像は1枚にまとめる。同じかどうかは、(1) ホストとクエリを除いたパス（`image.rakuten.co.jp` / `tshop.r10s.jp` / `www.rakuten.ne.jp/gold` / `thumbnail.image.rakuten.co.jp/@0_mall` は同じファイル）、(2) 見た目の指紋（dHash 64bit で違いが6以下、かつ縦横比が5%以内）。(2) が要るのは、店舗が同じ画像を別名で上げ直しているため（`thum/yol001_260601/03.jpg` と `yol001/03_260526.jpg` が同一、など）。リンク付きの画像（他の商品・クーポンへの導線）、横長の帯（横/縦が3超のボタン・見出し）、長辺200px未満のアイコンは説明に残す。
- **画像の縮小配信とCORSは `tshop.r10s.jp` だけ。** `?_ex=WxH` は正方形の枠に収めるだけで拡大はしない（縦横別の指定は効かない）。商品ページのオリジンには `Access-Control-Allow-Origin` を返すので、`crossOrigin="anonymous"` で読めば canvas で画素を読める。`image.rakuten.co.jp` と `www.rakuten.ne.jp` はCORSを返さない。
- **縦に極端に長い画像は縮小配信が失敗する。** 780x10810 などで 597 が返り、本文は1x1のSVG。画像としては読めてしまうので `onerror` は来ない。1x1なら失敗とみなして原寸を読む。縦長（縦/横が2超）の画像はギャラリーでは上端から見せ、拡大表示では幅に合わせて縦にスクロールさせる。
- **商品動画は楽天のプレーヤーを移設する。** JSONの `itemInfoSku.video.parameters` にあるのは静止画（`stillUrl`）と縦横比（`aspectRatioStr`）と、プレーヤーを描くスクリプト（`stream.cms.rakuten.co.jp/gate/play/?…&sel=.item-pc-movie-<番号>`）だけ。映像はトークン付きのHLSで、`<video>` に直接は流せない。そこで楽天の動画スクリプトが元のページの画像欄に描いたプレーヤー（`.item-pc-movie-<番号>`）を、購入エリアと同じく動画の枠へ移設する。ギャラリーでは1枚目の画像の隣に置く。
- **楽天のプレーヤーは自分で再生を始める。** 画面に6割見えたとき（IntersectionObserver）・読み込み終わったとき・マウスを載せたときに `video.play()` を呼ぶ（消音で）。ギャラリーで動画を選ぶだけで再生が始まるので、`video-guard.js`（MAINワールド）が `HTMLMediaElement.prototype.play` を包み、そのプレーヤーの中を押した直後（1秒以内の pointerdown / keydown）以外は `NotAllowedError` で断る。これはブラウザが自動再生を拒んだときと同じ応答で、プレーヤーは再生ボタンを出したまま待つ（始まった再生を `play` イベントで `pause()` する方式だと、プレーヤーは再生ボタンを消してしまい、操作バーも出ないまま何も押せなくなる。プレーヤーのコードから読んだ挙動）。止めるのは再構成したときだけ（`<html data-azr-no-autoplay>`）。店舗が説明に貼った `<video autoplay>` と `autoplay=1` の埋め込みも止める。
- **ライトボックスは左ペインの外に置く。** 左ペインは `position: sticky` で重なりの文脈を作るので、中に置くと z-index が閉じ込められ、移設した購入エリアのボタンが拡大表示の上に透けて出た。
- **取得に失敗したら再構成しない。** 商品名・価格が取れなければ、元のページをそのまま表示する。購入エリアの枠が DOMContentLoaded から3秒たっても無ければ、組み立てたレイアウトを片付けて元のページに戻す。
- **かごと購入手続きは1つのSPA。** どちらも `cart.step.rakuten.co.jp` で、`/cart` → `/shipping-address` → `/order-confirmation` とパスだけが変わる（ページの読み込みは起きない）。そのためページ種別は毎回 `location` から判定し直し、`boot.js` が経路の変化を見張ってモジュールを動かし直す。旧URLの `basket.step.rakuten.co.jp` は実際には `t3.basket.…` のようなサブドメイン付きで、そこから `cart.step.rakuten.co.jp/cart` へ転送される。**manifest のマッチにこのホストが無く、かご機能は一度も動いていなかった。**
- **金額は `window.__INITIAL_STATE__` から読む。** 楽天のかご画面のクラス名はCSSモジュールのハッシュ付き（`spacer--1O71j` など）でデプロイのたびに変わるので、表示テキストを漁るのは長持ちしない。状態には `shopItemSubtotals[ショップID]` として `itemTotalPrice` / `fee` / `couponUsage` / `pointsUsage` / `paymentAmount` / `pointValue` が入っている（キー名はページのバンドルのセレクタ定義で確認）。注文確認では同じものが `SUM` キーにまとまる。
- **`__INITIAL_STATE__` はページ読み込み時のスナップショットで、その後は更新されない。** 数量を変えてもクーポンを外しても古い値のまま（実機で確認）。そこで `state-bridge.js` が `fetch` と `XMLHttpRequest` を包み、SPAが受け取ったJSONに `shopItemSubtotals` などが入っていればそれを上から重ねる。これで数量変更やクーポン適用にパネルが追従する。
- **クーポンの項目は数値では入っていない。** 実物は `couponName` / `description` / `conditions` / `discountPrice`（`"700円OFF"` という**文字列**）/ `couponCode` / `selected` / `usable`。割引額も「4,000円以上」の条件も文言から読むしかないので、`coupon-model.js` の解析に通す。
- **商品ページのクーポンの本命は「フローティングクーポン」。** 元の商品ページで右下に出る「100円OFF … クーポンを獲得する」の枠は、HTMLにもJSONにも入っておらず、商品ページのバンドルが `api.coupon.rakuten.co.jp/search`（JSONP、`items=["itemId=…&price=<通常購入の最安値>&shopId=…"]`、`locId=101`）で取ってくる。**ログインしていないと `{"code":2}` しか返らない。Referer が商品ページ（`https://item.rakuten.co.jp/`）でない場合も、ログインしていても同じ `{"code":2}` になる。** 拡張の fetch には Referer が付かないので、`declarativeNetRequest` のセッション規則で service worker からの通信（タブに属さないもの）にだけ付ける。獲得は `api.coupon.rakuten.co.jp/acquireCoupon/json?getKey=…&key=<商品ページ用のキー>`。どちらもバンドルと同じ引数で service worker から呼び、クーポン欄の先頭に並べる。定期購入の無い商品では、バンドルと同じく定期購入専用のクーポンを除く条件（`otherCondFilters`）を付ける。
- **店舗のお知らせは獲得できるクーポンではない。** 「レビュー投稿でクーポン」「SALE×クーポンで最大40%OFF」のような店舗ページへのリンクも「クーポン」「OFF」を含むので文言では拾えてしまう。`getkey` の付いたリンクだけを「獲得する」にし、それ以外は「詳しく見る」でそのページを開く。
- **クーポンの選択モーダルは子の経路。** 「変更」を押すと `/order-confirmation/coupon-usage` に移り、閉じると `/order-confirmation` に戻る。`state-bridge.js` がパスの変化で重ねた応答を捨てていたため、適用直後の金額が消えて古い `__INITIAL_STATE__`（クーポン無し）に戻り、パネルが「最良クーポンを適用」に戻っていた。捨てるのはパスの先頭（画面そのもの）が変わったときだけにした。
- **1枚選ぶと、他のクーポンは全部 `usable: false` になる。** 理由は `alerts` に入る。`["選択済みのクーポンと併用が出来ません。"]` だけなら選び直せば使えるので候補に残し、`"5,000円以上お買い上げの場合に利用できます。"` のような条件の理由が付いていれば外す。切り替えるときは、今のクーポンのチェックを先に外してから新しい方を選ぶ。
- **クーポンの行は名前全体で探す。** 「【楽天スーパーSALE】対象ショップで「1注文合計1,500円…」「…3,000円…」のように先頭が同じクーポンが5枚並ぶことがあり、先頭18文字では取り違える。
- **押すときは pointerdown から始める。** 「変更する」は `element.click()` では反応しない（pointerdown/mousedown を見ている）。`realClick()` で pointerdown → mousedown → pointerup → mouseup → click の順に投げる。
- **押した結果は同期では読めない。** チェックの反映はReactの再描画のあとなので、`aria-checked` が変わるまで待つ。隠れているネイティブの `input` の `checked` は解除後も `true` のまま残ることがあり、これを見ると「選択済み」と誤読して未選択のまま確定してしまう。**判定は `aria-checked` だけを信じる。**
- **閉じたモーダルは 0x0 の要素としてDOMに残る。** `getClientRects().length` はそれでも 1 を返すので、「見えているか」は幅と高さで判断する。残骸の「変更する」を押しても何も起きない。
- **注文確認には複数のモーダルが同居している。** 「クーポン利用」と「変更する」を含む要素で探すと、いちばん外側の入れ物に当たって別のモーダルのボタンを押してしまう。クーポン名を含む**短いテキストの要素**を行として特定し、そこから同じモーダル内の「変更する」を辿る。スイッチ側から祖先を遡ると、ページ全体の入れ物までクーポン名を含むため、ページ下部の無関係なチェックボックス（メルマガ等）を掴む。
- **状態が届くたびにパネルを作り直さない。** 数百msごとに流れてくるので、内容が同じなら描き直さない。作り直すと、押そうとした瞬間にボタンが差し替わってクリックが消える。
- **状態はMAINワールドの小さなスクリプトで受け渡す。** `__INITIAL_STATE__` はページ側のグローバルで、コンテンツスクリプト（分離ワールド）からは見えない。`state-bridge.js` だけを `world: "MAIN"` で動かし、`postMessage` で渡す。**このとき金額まわりのキーだけをホワイトリストで抜き出す。** 状態には氏名・住所・電話・メール・カード下4桁（`ordererContactInfo` / `shippingInfo` / `paymentInfo`）が入っているので、拡張側へ流さない。
- **キャンペーンの一覧は自分で作る。** 楽天には「エントリーできるキャンペーンの一覧」も「エントリー済みの一覧」も無い。そこでトップページから `event.rakuten.co.jp` へのリンクを集め、1ページずつ開いて判定した結果を `chrome.storage.local` に貯める。その記録がそのまま「エントリー済み一覧」になる。
- **トップページのバナーは `rd.rakuten.co.jp/rat/?R2=<本来のURL>` で包まれている。** そのままでは対象かどうか判定できないので、`R2` を取り出してから見る。`l-id` / `scid` などは同じページの計測違いなので、クエリを落として重複を寄せる。
- **キャンペーンかどうかはページを開くまで分からない。** トップページのキャンペーンらしいリンクは60件前後あるが、大半はエントリー不要の特集ページ。実際に開いて「エントリーボタンの有無」で判定し、**エントリー不要と分かったページは7日間開き直さない**（2回目以降は数件で済む）。
- **`event.rakuten.co.jp` の判定は `coupon` のパス判定より先に置く。** `.../supersale/…/itemcoupon/` のようにURLに `coupon` を含むキャンペーンページがあり、順番を逆にするとクーポンページ扱いになってキャンペーンの処理が動かない（実際に6件がタイムアウトしていた）。
- **裏タブは実行を絞られる。** 重いキャンペーンページは読み込みだけで30秒を超えることがあるので、1ページあたり45秒まで待つ。同時に開くのは3タブ。
- **押しただけで「エントリーした」と言わない。** クリック後に表示が「エントリー済み」に変わったことを確かめてから記録する。
- **別のサイトへのリンクはエントリーボタンとみなさない。** SPU（`/campaign/point-up/everyday/point/`）には楽天モバイルのSPUページ（`network.mobile.rakuten.co.jp`）へ飛ぶ「エントリーはこちら」があり、押すとタブがそちらへ移って判定が返らず「時間切れ」になっていた。実際のエントリーボタンは `<button class="rcEntryButton-button">` で、リンクではなかった（トップから辿れる55ページと既知のキャンペーンを未ログインで確認。スポーツ・5と0のつく日・SPU内の案内の3件）。
- **裏タブを待っている間は service worker を起こしておく。** service worker はイベントもAPIの呼び出しも30秒ほど無いと止められ、メモリにある待ち（裏タブの結果・打ち切りのタイマー・スキャンの進み具合）が消える。裏タブの1ページは45秒まで待つので、その間だけ20秒ごとに拡張のAPIを呼ぶ（Chrome 110 以降、これで止めるまでの時間が延びる）。実際に止まる場面は再現できていない（DevTools などが付いていると止まらないため）。
- **状態ブリッジは、変わっていなければ抜き出し直さない。** 500msごとに状態全体を `slim()` と `JSON.stringify` に通していたのを、`__INITIAL_STATE__` の参照・重ねた応答・パスのどれかが変わったときだけにした。中身だけ書き換えられる場合に備え、5秒に1回は比べ直す。- **クーポンの適用はUIを押す。** 状態を書き換えてもサーバには伝わらない。「クーポン利用」カード（`div#confirm-use-coupon-card`、idは固定）の「変更」→モーダルで行を選ぶ→「変更する」の順に押す。押してよい要素は表示文言で選び、`注文を確定` などにマッチするものは何があっても押さない。

## 既知の制約 / TODO

- **楽天は使えるクーポンが1枚なら自動で適用することがある。** 複数あるときは「利用なし」のままのこともあった（みさき果樹園で確認）。どちらの場合も、今より多く引けるクーポンがあれば切り替える。
- **「得」は割引率ではなく割引額で比べる。** 21%OFFでも小計が小さければ300円OFFに負けるため、小計に当てはめた金額で比べる。
- **確認なしの自動切り替えは、注文確認を開いた最初の1回だけ。** 失敗しても押し直さない（パネルのボタンから本人がやり直せる）。楽天が先に選んだクーポンから自動で切り替わる場面は、ボタンでの切り替えでだけ確かめた（同じ処理を通る）。
- **クーポンの併用は扱えない。** 実物の利用条件に「併用不可」とあるとおり、店舗ごとに1枚。複数枚使える店舗での挙動は未確認。
- **「対象商品限定」のクーポンは判定できない。** 保有していても対象商品が入っていなければ `shopCoupons` に出てこないので実害は少ないが、条件の細部（対象商品・先着など）は文言のままで、こちらでは解釈していない。
- **確認した店舗は1つだけ。** クーポンの項目のキー名は店舗やクーポン種別で違う可能性があるため、`normalizeCoupon` は候補キーを順に見て、取れなければ文言から推定する作りにしてある。
- **キャンペーンはトップページに出ているものしか拾えない。** メールやアプリでしか案内されないキャンペーン、ジャンル別ページの奥にあるものは対象外。必要なら「URLを指定して実行」に足す。
- **エントリーの判定はボタンの文言頼み。** 「エントリー」「エントリー済み」といった表示が変わると取りこぼす。楽天カードや楽天モバイルなど `event.rakuten.co.jp` 以外のドメインのキャンペーンも今は見ていない。
- **かごの送料はかご画面では金額が出ない。** `shippingFeeType` で無料かどうかが分かるだけで、金額は購入手続きに進んで初めて `fee` に入る。かごのパネルでは送料を「購入手続きで確定」とし、お支払い予定に「（送料がある場合は別）」を添える（無料でない店が1つでもあるときだけ）。
- **検索結果の広告非表示は対象が無い。** 楽天の検索結果に広告ラベルが見当たらないため、この機能は現状なにもしない。削除するか、別の用途（実質価格の表示など）に作り替えるかは要判断。
- クーポンの解析は表示テキストのパターンマッチ。「対象商品のみ」等の条件は判定できない。
- 商品ページで、店舗が独自に置いたスクリプトがコンソールにエラーを出すことがある（元のDOMを隠すため）。表示や購入操作には影響しないことを確認済み。
